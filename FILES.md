# Manual Save and Restore

At the bottom of Settings, choose JSON or SQLite and click Save to download one file. The file contains the current top ten completed-game results and all six gameplay settings. It does not contain the active board. Save captures one detached snapshot; a later game completion cannot change the file being prepared. Hiding Settings hides both file buttons and the format choice.

Click Restore and choose either format. Content determines the format, including when a file has a different extension. Cancellation does nothing. A successful restore replaces the session leaderboard and all settings, updates their cookies and URL parameters, and pauses running play. It preserves the active board, queue, hold, score and bonuses. Resume explicitly when ready. Restored scores remain session-only and clear on reload; configuration continuity is separate.

The names are tetris-save.json and tetris-save.sqlite. Files must be at most 2 MiB. JSON accepts strict UTF-8 with one optional BOM. Duplicate member names, extra/missing fields, invalid settings, duplicate result IDs, more than ten results, unsafe or negative scores and impossible/noncanonical UTC timestamps reject the entire file. No valid subset is loaded. A clear error leaves results, settings, cookies and URL unchanged after validation failure.

The [JSON Schema](schemas/tetris-save.schema.json) uses draft 2020-12. Runtime structural validation enforces all its constraints, followed by real-date round trips and unique-ID checks. A lexical pass detects duplicate decoded names before structural validation; a parsed JSON object or schema alone cannot recover duplicate names. Independent schema validation with an explicit date-time format checker tests the same corpus. No runtime schema compiler or eval is needed.

Version 1 has exactly formatVersion=1, results and settings. Each result has an immutable lowercase UUID v4 id, a non-negative integer score through 9007199254740991 and a canonical UTC timestamp such as 2026-01-01T00:00:00.000Z. Sort order is descending score, ascending completion time, then ascending ASCII ID. IDs and timestamps are preserved in both formats.

SQLite is an ordinary standalone SQLite 3 database. PRAGMA user_version is 1 and application_id is 1413829714. high_scores(id TEXT PRIMARY KEY NOT NULL, score INTEGER NOT NULL CHECK(score >= 0 AND score <= 9007199254740991), timestamp TEXT NOT NULL) stores results. settings(key TEXT PRIMARY KEY NOT NULL, value TEXT NOT NULL) has exactly one row per canonical setting: ghost, hardDrop, next, hardDropLock, lock and hold. Inspect it with any compatible SQLite reader. Saving uses bound inserts in one transaction. Restore uses a separate in-memory database, fixed trusted queries, metadata/schema/ordinary-table/integrity/storage-class checks and full semantic validation; it never executes imported schema SQL or changes the source file.

A validated restore commits host persistence before application state. If host writes fail, previous cookie values and URL are restored and read back. If rollback cannot be confirmed, the app reports that fact and blocks further persistence until reload/reconciliation; it does not falsely report success. Browser JavaScript cannot make cookies/history crash-atomic or recover inaccessible cookie expiry metadata. This does not weaken invalid-file non-mutation. File operations and settings edits are serialized from byte reading through completion, and temporary download URLs are released.

All SQLite JavaScript/Wasm and schema assets are bundled locally. No file is uploaded, watched, synchronized or restored automatically. No backend or separate runtime installation is required.
